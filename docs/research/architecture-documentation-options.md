# Architecture documentation options for chaptour

Research note, not a decision. Written to inform a future ADR (or a maintainer's own call) on whether chaptour should adopt a heavier architecture-documentation framework on top of what already exists. This is pure research output — it does not modify `CONTEXT.md`, `docs/adr/`, or `AGENTS.md`.

## What chaptour already has

Before comparing external frameworks, here's what's actually in the repo today, since every option below has to justify itself against this baseline rather than a blank slate:

- **`CONTEXT.md`** (repo root): a single-file domain glossary, ~39 lines. Nine terms (Author, Follower, Book, Update, Announcement, Tour Date, Cover Reveal, Past Updates, Buy Link, Merch Link), each with a one-paragraph definition and an explicit "_Avoid_: ..." line calling out rejected synonyms (e.g. "Author... _Avoid_: creator, user"). No architecture content — purely ubiquitous-language vocabulary.
- **`docs/adr/`**: 15 numbered ADRs (`0001`–`0015`), each a single file with an H1 title stating the decision and **one paragraph** of body text. Every ADR follows the same rhetorical shape: state the tension, name the alternative(s) considered, say what was rejected and why, state the decision, and often close with an explicit "revisit when X happens" trigger (e.g. ADR-0007: "Revisit this when self-serve Author signup... actually gets built"; ADR-0011: "Once the database holds data worth protecting, add a manual review/approval step... don't carry this automation forward by default"). Decisions span stack choice (0001: .NET/Azure over a more AI-tooled stack), product scope (0002: curated onboarding), data lifecycle (0003: archive not delete), **framework rejection (0004: Razor Pages/MVC, not Blazor — rejected for adding unnecessary complexity, SignalR/WASM overhead, and because the author has no Blazor fluency)**, client-side tooling (0005: Alpine.js CSP build), local dev (0006: Aspire), auth (0007: external logins only, no local passwords), hosting (0008: App Service not Container Apps), CI/CD platform (0009: GitHub Actions), deploy gating (0010: no manual approval gate), migrations (0011: automatic), testing (0012: integration tests via Aspire), auth-to-cloud (0013: OIDC federated credentials), branching (0014: trunk-based/always-shippable main), and security (0015: automated dependency scanning). None of the 15 is itself about *how to document architecture* — they're all product/technical decisions.
- **`AGENTS.md`**: two lines pointing at `docs/agents/issue-tracker.md` (GitHub Issues) and `docs/agents/domain.md` (how to consume the domain docs).
- **`docs/agents/domain.md`**: instructions for AI agents on how to use `CONTEXT.md` + `docs/adr/` before exploring the codebase — read them first, use the glossary's exact vocabulary, flag when new work contradicts an existing ADR, and (important for scaling this pattern) explicitly says the docs are created *lazily*, by a `/domain-modeling` skill, "when terms or decisions actually get resolved" — not scaffolded upfront. It also documents a multi-context layout (`CONTEXT-MAP.md` + per-context `CONTEXT.md`/`docs/adr/`) for when the repo outgrows a single bounded context, which chaptour is not at yet.

The pattern across all of this: small, single-purpose files; decisions recorded as prose, not tables/matrices; nothing scaffolded speculatively; explicit "avoid this term" / "revisit this decision" markers that make the docs actionable rather than archival. ADR-0004 is the clearest signal of the project's own stated values: Blazor was rejected specifically because it would mean "juggling per-component render-mode decisions" and using a framework the maintainer isn't fluent in, when a simpler, already-familiar option covered the actual need.

## Option 1: arc42

**What it actually produces.** arc42 is a template with **12 fixed sections**, per its own reference documentation (docs.arc42.org, "Home" and "Overview" pages): Introduction & Goals, Constraints, Context & Scope, Solution Strategy, Building Block View, Runtime View, Deployment View, Crosscutting Concepts, Architectural Decisions, Quality Requirements, Risks & Technical Debt, and Glossary. It's a document structure (Word/AsciiDoc/Markdown templates are distributed from arc42.org), not diagrams — each section is meant to hold prose plus whatever diagrams the author chooses to add. Section 9, "Architectural Decisions," and section 12, "Glossary," overlap directly with what chaptour already has as separate files.

**Overhead for this project.** arc42's own FAQ is explicit that the full template is not meant to be filled in wholesale: "Please don't _fill in everything_. Document **only what your stakeholders need**" (faq.arc42.org, Question B-1), and describes the sections like compartments in a cabinet — the cabinet has value even with empty compartments, but everything documented costs future maintenance. The arc42 homepage (arc42.org) says the template "suits large and small teams, agile or not," and tags itself for "lean" agile users, "thorough" (large/critical-system) users, and "essential"-documentation users — but this is arc42 describing itself as broadly applicable, not offering a concretely trimmed small-project variant; there's no official "arc42-lite" section subset published anywhere I could source. For chaptour specifically, realistically useful sections would be: **Context & Scope** (external systems: Azure SQL, Blob Storage, external identity providers, email delivery — genuinely useful and not currently written down anywhere), **Solution Strategy** (a short "why .NET/Azure, why Razor Pages not Blazor, why App Service" overview — though this already exists as ADRs 0001/0004/0008 and would be pure duplication if repeated as prose), **Deployment View** (App Service + staging slot + swap — useful, not documented today), and **Crosscutting Concepts** (CSP/Alpine.js, auth model — partially covered by ADR-0005/0007). Sections like **Quality Requirements** (formal quality-attribute scenarios/trees), **Risks & Technical Debt** as a standing tracked register, and the full **Building Block View** hierarchy (white-box/black-box decomposition down to component level) are built for teams coordinating across multiple people/subsystems where a shared, formal reference is worth the upkeep cost — for a solo maintainer who already holds the whole system in his head, they're the "empty compartments" arc42 itself says are fine to skip, except here they'd likely stay empty forever rather than get filled in later, which is its own form of dead weight (a template with 8 of 12 sections marked "N/A" is not obviously better than no template).

**Overlap risk.** High, and arc42 says so implicitly by having its own ADR section — adopting arc42's "Architectural Decisions" section (9) would either duplicate `docs/adr/` or require pointing that section at the existing ADR folder instead of writing decisions twice. Same for "Glossary" (12) vs. `CONTEXT.md`. The clean move, if arc42 were adopted, would be to *not* fill in sections 9 and 12 at all and instead have them read "see `docs/adr/`" / "see `CONTEXT.md`" — which is exactly the kind of thin cross-reference arc42's own philosophy supports, but also means 2 of the 12 sections are immediately hollowed out before you've written a word of new content.

**Tooling/.NET-Azure ecosystem.** arc42 ships templates for Word, AsciiDoc, and Markdown/AsciiDoctor toolchains (docs.arc42.org), plus a general-purpose "arc42-generator" for building HTML/PDF/DOCX output from AsciiDoc source. None of this is .NET- or Azure-specific — it's a generic documentation template usable from any stack. There's no Visual Studio/VS Code-native arc42 tooling beyond generic Markdown/AsciiDoc editing support, and no meaningful .NET ecosystem integration to report; I did not find one, and don't want to overstate this.

Sources: [arc42.org](https://arc42.org), [docs.arc42.org — Home](https://docs.arc42.org/home/), [arc42 FAQ — Question B-1: Which parts of arc42 are essential, which are optional?](https://faq.arc42.org/questions/B-1/), [docs.arc42.org — Section 5, Building Block View](https://docs.arc42.org/section-5/)

## Option 2: The C4 model

**What it actually produces.** Per c4model.com itself, C4 is "a set of hierarchical diagrams" (not a document template) across four levels: **System Context** (the system and the people/external systems around it), **Container** (the high-level technology choices — e.g. a web app, a database — and how they communicate), **Component** (the significant structural building blocks inside a container), and **Code** (classes/interfaces, usually generated rather than hand-drawn). C4model.com also describes supplementary diagram types (System Landscape, Dynamic, Deployment). The output is diagrams, full stop — there is no C4 equivalent of an arc42 "Introduction & Goals" or "Quality Requirements" section; it deliberately doesn't cover prose narrative, decisions, or requirements at all.

**Is it a competitor to arc42, or complementary?** Verified from both sides, as requested:
- From arc42's side: arc42's own FAQ (faq.arc42.org, Question B-17, "What about arc42 and C4?") states C4 "has _many_ similarities to a few sections from arc42, but omits certain parts (e.g. quality requirements, crosscutting concepts, risks and a few others)" — i.e., arc42 positions C4 as a partial, diagram-only overlap with a few of its own sections, not a substitute for the whole template.
- From C4's side: c4model.com's FAQ states explicitly: "Yes, many teams do [use C4 with arc42], and the C4 model is compatible with the arc42 documentation template," and gives a direct mapping — arc42's "Context and Scope" section pairs with the C4 System Context diagram, arc42's "Building Block View" levels 1–3 pair with C4's Container, Component, and Code diagrams respectively.

So this is confirmed as a **complementary notation, not a competing framework**: C4 is what you'd draw *inside* an arc42 section (or inside a standalone Markdown doc, or inside an ADR), not an alternative to having a written template at all. The c4model.com FAQ does not address whether C4 replaces written documentation generally — it only confirms the arc42 mapping, so I'm not asserting more than that.

**Overhead for this project.** Very low, and that's the point. C4 isn't a "framework to adopt" in the same sense as arc42 or design docs — it's a diagramming convention you can apply to a single PNG or Mermaid diagram whenever a picture would help. For chaptour, a single **System Context diagram** (chaptour, Authors, Followers via email, Azure SQL, Blob Storage, the external identity providers from ADR-0007) and maybe one **Container diagram** (the web app, SQL, Blob Storage, email sending) would likely be the entire useful footprint — Component and Code-level C4 diagrams are typically not worth hand-maintaining for a single-project monolith with one maintainer, since the code itself is the fastest way to answer "what components exist" at that scale.

**Overlap risk.** Minimal — C4 diagrams don't compete with `CONTEXT.md` (vocabulary) or `docs/adr/` (decisions with rationale); a Context/Container diagram is a genuinely new artifact type chaptour doesn't have today (nothing currently shows the external dependencies visually). If arc42 is *not* adopted, C4 diagrams could simply live as standalone files (e.g. `docs/architecture/context-diagram.md` with an embedded Mermaid C4 diagram) without needing any surrounding template at all.

**Tooling/.NET-Azure ecosystem.** C4model.com documents multiple tool integrations, most notably **Structurizr** (built by the same author, Simon Brown, as a "diagrams as code" tool with a DSL) and community tooling for **Mermaid** and **PlantUML**, both of which render directly in GitHub Markdown previews and VS Code with common extensions — this is the most practical path for a solo .NET dev who wants a diagram in a Markdown file without new infrastructure. There's nothing .NET/Azure-specific in C4 itself (it's stack-agnostic by design), but Mermaid-in-Markdown works with zero new tooling since GitHub already renders it.

Sources: [c4model.com](https://c4model.com), [c4model.com/faq](https://c4model.com/faq), [arc42 FAQ — Question B-17: What about arc42 and C4?](https://faq.arc42.org/questions/B-17/)

## Option 3: Google-style design docs

**What it actually produces.** There is no single official Google specification for this — Google's own public engineering-practices site (google.github.io/eng-practices) documents code review standards (the Reviewer's Guide and Author's Guide) but, as far as I could find via direct inspection and search, does **not** itself publish a design-doc template. The most credible and widely cited primary(-ish) source is Malte Ubl's essay "Design Docs at Google" (industrialempathy.com/posts/design-docs-at-google), written by a Google engineer describing the internal practice from firsthand experience. **I want to be explicit about the sourcing honesty point the task asked for**: this is a semi-official engineer's personal account of an internal cultural practice, not an official Google specification with a rigid mandated template — Ubl's own essay says as much: "Design docs are informal documents and thus don't follow a strict guideline for their content. Rule #1 is: Write them in whatever form makes the most sense." With that caveat, the structure he describes is: **Context and Scope** (objective background), **Goals and Non-Goals**, **The Design** (overview, then a level of detail sufficient for review), **Alternatives Considered** (with trade-offs — this is the load-bearing section, per Ubl), and **Cross-cutting concerns** (security, privacy, observability), with optional system-context diagrams, API sketches, and pseudo-code added only where they earn their place. Typical length: "10-20ish pages" for a larger project, or 1-3 page "mini design docs" for smaller changes. It's a single living document per *proposed change*, not a per-repo standing reference — written before a project starts, reviewed by peers/senior engineers, and then generally left as historical record once the work ships.

**Overhead for this project.** This is the one option in this list that isn't "one document per repo" — it's "one document per non-trivial change or feature," written *before* building it. For a solo maintainer, the review/circulation step (Ubl describes cross-team review meetings) obviously doesn't apply, but the core discipline — write down the goals, non-goals, and alternatives considered *before* writing code, for anything non-trivial — maps closely to something chaptour is already doing informally: every existing ADR already contains an implicit "alternatives considered" section (each one states what was rejected and why). The mini design-doc (1-3 pages) is realistically the only version worth adopting here; a 10-20 page design doc for a one-person greenfield app is disproportionate.

**Overlap risk.** This is the most interesting overlap case of the four: a "mini design doc" for a feature and an ADR for a decision are close enough in spirit that adopting this wholesale risks producing two parallel systems for the same thing (a design doc's "Alternatives Considered" section is structurally almost identical to an ADR's body). The place a design doc *wouldn't* overlap with ADRs is scope broader than a single decision — e.g. "how the Follow/Update/email flow works end-to-end" is a design worth writing once, whereas each individual technical choice inside it (archive-not-delete, curated onboarding, etc.) already has its own ADR. Used that way, a design doc is a *narrative that stitches ADRs together*, not a replacement for them.

**Tooling/.NET-Azure ecosystem.** None to report, and none should be expected — this is a writing convention, not a tool. It's typically just a shared doc (Google Docs, internally) or, in an OSS/repo context, a Markdown file in the repo. No .NET/Azure-specific angle exists here.

Sources: [Design Docs at Google — Malte Ubl](https://www.industrialempathy.com/posts/design-docs-at-google/), [google.github.io/eng-practices](https://google.github.io/eng-practices/) (checked directly — confirms the site covers code review guidelines, not a design-doc template, so no design-doc claim is attributed to it beyond what Ubl's essay independently describes)

## Option 4: Michael Nygard's original ADR format (the format `docs/adr/` likely descends from)

**What it actually produces.** Nygard's 2011 post "Documenting Architecture Decisions" (cognitect.com/blog/2011/11/15/documenting-architecture-decisions) is the primary source for the ADR convention that essentially the entire industry's "lightweight ADR" tooling (adr-tools, MADR, etc.) descends from. His proposed structure per record: **Title** (a short noun phrase, numbered sequentially), **Context** ("the issue that is motivating this decision," described in value-neutral language), **Decision** (stated in full sentences, active voice: "We will…"), **Status** (proposed / accepted / deprecated / superseded), and **Consequences** (the resulting context, both good and bad, "because these decisions affect [...] the team and project in the future"). His explicit rationale for keeping them short: "Large documents are never kept up to date. Small, modular documents have at least a chance at being updated" — and immutability matters because a superseded decision stays on record rather than being silently deleted, preserving the reasoning for why something changed.

**Overhead for this project — and the honest comparison to what's already there.** chaptour's existing `docs/adr/` already **is** a working, lightweight ADR practice — just a further-compressed variant of Nygard's format: each of the 15 records collapses Context/Decision/Consequences into a single paragraph and drops the explicit Status field (status is implicitly "accepted," with supersession handled by prose like ADR-0007's "Revisit this when..." rather than a formal "Superseded by ADR-000X" header). This is not a gap to fix by "adopting" Nygard's format — chaptour has effectively already made that adoption decision, informally, and arguably improved on it for this project's scale: a solo maintainer doesn't need a `Status: proposed` step (there's no one else to propose to), and one paragraph beats Nygard's ~5-section skeleton when the whole point, per Nygard's own stated rationale, is to keep the document small enough that it actually gets written and kept current. The only thing genuinely missing relative to Nygard's original is the explicit **Status** field for marking supersession formally (right now it's implied by prose, e.g. ADR-0011 says "this is a deliberate, revisit-later choice" rather than expecting a future ADR-00xx to carry a "Supersedes: 0011" header) — a small, cheap addition if/when an ADR actually gets superseded, not a reason to restructure the whole set.

**Overlap risk.** This isn't really a fourth "option" competing with arc42/C4/design docs in the same sense — it's the existing baseline, already in place, doing its job. Its relevance to this report is as the reference point the other three options get evaluated against: chaptour doesn't need to "adopt ADRs," it needs to decide whether anything *bigger* than ADRs is worth adding on top.

**Tooling/.NET-Azure ecosystem.** Generic ADR tooling exists (`adr-tools`, npm's `adr-log`, VS Code snippets/extensions for ADR templates like MADR), all stack-agnostic Markdown-file conventions — nothing .NET/Azure-specific, and chaptour isn't using any of them today (its ADRs are hand-written plain Markdown, which is consistent with the "don't add tooling you don't need" pattern visible elsewhere in this repo, e.g. ADR-0009 rejecting a second CI platform to avoid maintaining two systems).

Sources: [Documenting Architecture Decisions — Michael Nygard, cognitect.com](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)

## Recommendation

**Don't adopt arc42 (or any full document-template framework), and don't adopt Google-style design docs as a standing per-repo artifact. Do add two small, narrowly-scoped things: (1) a couple of C4-style diagrams as plain Markdown/Mermaid files, and (2) an explicit `Status`/`Supersedes` line on ADRs going forward. That's it.**

Why, concretely:

1. **This repo's own ADRs already answer the question "how much architecture-documentation process does chaptour want."** ADR-0004 didn't just reject Blazor for technical reasons — it rejected a *more capable* option in favor of one that matched the maintainer's existing fluency and the project's actual needs, and explicitly called out "juggling per-component render-mode decisions" as the kind of overhead not worth paying for here. arc42's 12-section template is the documentation-process equivalent of Blazor: more capable, built for a different scale of team (arc42.org's own "thorough" tag is explicitly for "very large or critical systems with hard quality requirements"), and would leave most sections either duplicating `CONTEXT.md`/`docs/adr/` or sitting empty. A greenfield, solo-maintained repo with 15 ADRs and a 39-line glossary is not an under-documented project waiting for a template — it's a project whose documentation is working, in a shape it already chose deliberately.

2. **arc42's two most relevant sections (Architectural Decisions, Glossary) are the two chaptour has already solved better for this scale.** Folding them into arc42 would mean either duplicating content across two places (a maintenance liability Nygard's own rationale for ADRs warns against directly: "large documents are never kept up to date") or hollowing out those arc42 sections into pointers back to the files that already do the job — at which point you've added a wrapper, not new documentation.

3. **What chaptour is actually missing isn't structure, it's a picture.** Nothing today shows, at a glance, what's talking to what — the App Service, Azure SQL, Blob Storage, external identity providers (Google/Microsoft per ADR-0007), and outbound email all exist only as facts scattered across 15 separate ADR paragraphs. This is precisely the gap C4's System Context and Container diagrams fill, and — confirmed from both arc42's and C4's own primary sources — C4 is explicitly designed to be used *without* requiring the rest of arc42 around it. Concretely: one Mermaid C4-Context diagram and one Container diagram, committed as plain Markdown (e.g. `docs/architecture/`), rendering natively in GitHub's Markdown preview with zero new tooling. This is a few hours of work, not a documentation program.

4. **Google-style design docs are the right *idea* at the wrong *granularity* for a per-repo standing doc set** — but worth keeping in mind as a per-feature habit rather than a repo artifact. chaptour's ADRs already function as design docs' most valuable section (Alternatives Considered) at decision-granularity; introducing a separate "design doc" layer risks exactly the duplication problem described above. If a future feature is genuinely complex enough to want a narrative walkthrough before building it (e.g., "how the follow/email pipeline works end-to-end," stitching several existing ADRs together), write a one-off Markdown doc for it *then*, in `docs/research/` or wherever it best fits — don't scaffold a standing "design docs" folder/process now for a need that hasn't materialized. This mirrors `docs/agents/domain.md`'s own stated philosophy: domain docs are "created lazily... when terms or decisions actually get resolved," not scaffolded upfront on the chance they'll be needed.

5. **Nygard's ADR format**: no action needed beyond one small addition. Add an explicit `Status: Accepted` / `Superseded by ADR-00xx` line to ADRs going forward (cheap, and closes the one real gap versus Nygard's original format) — but this is a tweak to an existing convention, not a new framework, and doesn't need a research report or an ADR of its own to justify.

**Net effect if this recommendation is followed:** no new standing template, no restructuring of `CONTEXT.md` or `docs/adr/`, one new lightweight artifact type (a couple of C4 diagrams, informally, maybe under `docs/architecture/`), and one optional small convention tweak (Status lines on future ADRs). If the maintainer later hits a concrete pain point this doesn't solve — e.g. onboarding a second contributor who needs more context than 15 ADR paragraphs give them — that's the moment arc42-as-a-wrapper-around-existing-docs becomes worth reconsidering, and it would make a good future ADR in its own right at that point, not before.
