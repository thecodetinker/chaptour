# Server-rendered Razor Pages/MVC, not Blazor

Profiles are fully public and depend on discovery and sharing (a link in a tweet, a QR code at a signing), which means SEO and fast anonymous first-load matter for most of the site's traffic. The only authenticated, interactive surface is the small Author dashboard (a handful of forms). Blazor was the default candidate as the modern .NET web UI framework, but was rejected: its interactive render modes (Server/WebAssembly) either add a SignalR connection or a client download, both unnecessary for a mostly-read, mostly-anonymous site, and static SSR render mode would still mean juggling per-component render-mode decisions. The author also has prior experience with Razor Pages/MVC and none with Blazor, which matters more here than the framework choice itself — reviewing agent-generated code is easier in a framework already fluent. We're using plain ASP.NET Core Razor Pages/MVC everywhere, including the Author dashboard, rather than mixing two view engines.
